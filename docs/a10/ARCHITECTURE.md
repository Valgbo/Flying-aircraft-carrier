# A-10 Simulator — Architecture & Contracts

The working contract for everyone (human or agent) building the A-10 simulator. `PLAN_A10.md`
says **what** we build and why; this file says **how the pieces fit together**. If code and this
file disagree, fix one of them — do not leave it.

The carrier app (`/`, `docs/ARCHITECTURE.md`) keeps working unchanged. The A-10 app is a second
page (`/a10/`) in the same repository and build.

## 2. Conventions

### Units

SI everywhere in `core/` (m, kg, s, N, rad, K). Display units only in the UI, HUD and cockpit:
knots, feet, ft/min, nautical miles, degrees, milliradians. Conversions in `core/units.ts`
(`KT`, `FT`, `NM`, `LB`, `LBF`, `DEG`, `MIL`, `msToKt()` …). Names ending `Deg`, `Kt`, `Ft`
hold display units; everything else is SI.

### Frames (`core/frames.ts`)

- **World:** +Y up, +X east, **−Z north**, metres. Origin at the centre of the 64 × 64 km map,
  y = 0 at sea level. x, z ∈ [−32 000, 32 000].
- **Body (aircraft):** +X right wing, +Y up, **−Z nose**. Origin = the reference centre of
  gravity (CG). The body→world rotation is a three.js `Quaternion` (`aircraft.orientation`).
  A three.js camera with the identity rotation looks along body −Z, so the cockpit camera and
  the body frame line up.
- **Body angular velocity** (`aircraft.angularVelocity`) uses the right-hand rule about the body
  axes: ω.x > 0 nose up, ω.y > 0 nose LEFT, ω.z > 0 roll LEFT. Write flight equations with the
  aviation accessors `rollRate()` p (+ right wing down), `pitchRate()` q (+ nose up),
  `yawRate()` r (+ nose right), `omegaFromRates()`.
- **Attitude:** heading ψ ∈ [0, 2π), 0 = north, clockwise; pitch θ + nose up; bank φ + right wing
  down. `attitudeFromQuaternion`, `quaternionFromAttitude`.
- **HUD angles:** azimuth + right, elevation + up, of a direction relative to the boresight
  (body −Z): `hudAnglesFromBodyDir`, `bodyDirFromHudAngles`, `hudPlaneFromBodyDir` (gnomonic,
  for drawing on a flat collimated plane).
- **Vehicle local frame:** same handedness as the body frame (+X right, +Y up, −Z forward),
  origin on the ground under the hull centre; `vehicle.heading` uses the compass convention.
- **Precision.** No floating origin: |x|, |z| ≤ 32 km keeps float32 error under 4 mm, and
  three.js computes model-view matrices in float64. Keep vertex data LOCAL to each mesh (terrain
  tiles, decals) and place meshes with their object transform. The cockpit and HUD are drawn in
  body coordinates in their own passes, so they never shake.

### Time

- `sim.time` = simulated seconds since the flight started; it advances only in `stepSim`.
- View code animates with `sim.time` or with `frameInfo` (`view/frame.ts`); never with wall
  clock (pause and screenshots depend on it). Purely cosmetic view randomness may use
  `Math.random()`; the core never does.

## 3. The simulation core

### State

`Sim` (`core/types.ts`) is one plain mutable object created by `createSim()` (`core/sim.ts`):

| Field | Type (file) | Written by |
|---|---|---|
| `options` | `SimOptions` (types.ts) | createSim |
| `time`, `stepCount` | | stepSim |
| `rng.{gun,weapons,damage,targets,air,misc}` | `RngStreams` (rng.ts) | each system its own stream |
| `input` | `PilotInput` (types.ts) | input module, once per frame before stepping |
| `commands` | `Command[]` (types.ts) | input / UI / cockpit clicks; consumed by avionics `applyCommands` |
| `aircraft` | `AircraftState` (flight/types.ts) | flight (gun adds `externalForceBody/MomentBody`) |
| `avionics` | `AvionicsState` (avionics/types.ts) | avionics |
| `gun` | `GunState` (weapons/types.ts) | weapons |
| `stores` | `StoresState` (weapons/types.ts) | weapons |
| `projectiles` | `ProjectileState` (weapons/types.ts) | weapons |
| `world` | `WorldState` (world/types.ts) | world |
| `targets` | `TargetsState` (targets/types.ts) | targets |
| `sensors` | `SensorsState` (sensors/types.ts) | sensors |
| `debrief` | `DebriefState` (debrief/types.ts) | every system appends records; debrief scores |
| `events` | `SimEvent[]` (types.ts) | every system appends; the frame loop drains |

Each module's state type lives in its own `types.ts`, which that module owns. **A module may add
fields to its own types; it must not rename or remove a field another module reads.**
`core/types.ts` (Sim, PilotInput, Command, SimEvent) is foundation-owned: ask for a new command
or event variant in your report and use the closest existing one meanwhile.

### Stepping

- Fixed step `SIM_DT = 1/120 s`. `SimDriver` (view) runs whole steps from a real-time
  accumulator, at most `MAX_STEPS_PER_FRAME = 5` per frame (a slow frame slows time instead of
  destabilising it). Paused or off the flight screen: no steps.
- Before the steps of a frame, `onBeforeSimSteps` listeners run (the input layer writes
  `sim.input` and queues commands there). After the steps, `onSimFrame` listeners receive the
  frame's events.
- **Step order** (`stepSim`, `core/sim.ts`):

| # | Call | Module | Notes |
|---|---|---|---|
| 1 | `applyCommands` | avionics | switches, modes, HOTAS; may forward to flight/weapons/sensors setters |
| 2 | `stepFlightControls` | flight | stick + trim + SAS + PAC + autopilot → surface positions |
| 3 | `stepFlight` | flight | saves `prev*`, integrates 6-DOF, applies and clears external forces, derives air data, detects ground contact |
| 4 | `stepGun` | weapons | spin, emits rounds at exact sub-step times **between `prev*` and the new state**, writes recoil into `externalForceBody/MomentBody` for the next step |
| 5 | `stepStores` | weapons | consent/CCRP/Maverick releases → store bodies |
| 6 | `stepProjectiles` | weapons | rounds and bodies move; impacts vs terrain and vehicles; calls targets for damage |
| 7 | `stepTargets` | targets | movement, behaviour, fires, heat, cook-offs |
| 8 | `stepSensors` | sensors | pod and seeker tracking of the moved vehicles |
| 9 | `stepFireControl` | avionics | gun / CCIP / CCRP solutions from the new state |
| 10 | `stepWarnings` | flight | stall, over-g, altitude, ground-collision |
| 11 | `stepWorld` | world | weather changes |
| 12 | `stepDebrief` | debrief | scoring |

### Determinism

Same seed + same input sequence ⇒ identical state (tested). The core never uses `Math.random`,
`Date`, `performance.now` or iteration over `Set`/`Map` built in a non-deterministic order. Each
system draws only from its own `sim.rng` stream.

### Events and commands

- `SimEvent` (types.ts) carries one-shot outcomes with their sim time `t` and plain `{x,y,z}`
  positions (copies). Effects, audio, UI and the debrief consume them; nobody else reacts to a
  state change by polling if an event exists for it.
- `Command` (types.ts) carries discrete pilot actions. The input layer resolves short/long
  presses (TMS/DMS/China hat/coolie: long = held ≥ 0.4 s) before queuing.
- **Command values as the input layer queues them** (the avionics module must handle every
  one): `masterArm` and `laserArm` arrive as explicit `'ARM'`/`'SAFE'` (the key toggles from the
  current state); `gunPac` `'cycle'`; `tgpPower` `'toggle'`; `altSource` `'cycle'`;
  `masterMode` `'next'` (or `'previous'`, both skipping modes that are not available); `profile` ±1; `soi` an explicit `'HUD'|'LMFD'|'RMFD'`;
  `tms`/`dms`/`coolie` `{dir, long}`; `chinaHat` `{fwd|aft, long}`; `sensorPicture` `'cycle'`;
  `sensorZoom` ±1; `flaps` `0|1|2` (next position) or `'up'`/`'down'`; `gear` `'toggle'`;
  `autopilot` `'toggle'`/`'mode'`; `altitudeAlert` in metres above the ground, 0 = off (steps
  off, 200, 500, 1,000, 1,500, 2,000 ft); `steerpoint` ±1; `jettison` `{stations: 'all'}` only
  after a 0.4 s hold. `mfdPage`, `osb` and `rearm` come from the cockpit and UI.
- Continuous controls are in `PilotInput`: stick, pedals, two throttles, the two-stage gun
  trigger (`trigger: 0 | 1 | 2`; 1 = PAC-1 detent, 2 = fire; the input layer already applies the
  one-stage realism rule), weapon release (held), speed-brake switch (the key latches ±1 until
  `aircraft.speedBrakeCmd` reaches 1 or 0, so that field must keep moving with the switch), trim
  hat, slew, laser button.
- **Event timing:** `gunStart` carries the exact sim time of the burst's first round and
  `gunStop` the time of its last (sub-step accurate), so audio can start and stop the gun
  sample-accurately. Switch and mode changes made by commands emit `switch {name, value}`
  (audio plays the click).

### Allocation

No allocations per step or per frame in hot paths: module-level scratch `Vector3`/`Quaternion`,
pools (rounds are a structure-of-arrays pool of 1,024). Events allocate small objects; that is
fine (≤ a few hundred per second).

## 4. Module contracts (what others may rely on)

Each module keeps the exports below with the meaning given. Stand-in implementations exist for
every one of them, so all modules compile and run from day one.

### World — `core/world`

`generateTerrainData(seed): TerrainData` (pure, transferable typed arrays) ·
`createTerrain(data): Terrain` · `createFlatTerrain(height?, size?)` (tests) ·
`createWorldState(terrain)` · `windAt(world, position, out)` · `stepWorld` · ISA functions
(`densityAt`, `pressureAt`, `temperatureAt`, `speedOfSoundAt`, `casFromTas`, `tasFromCas`).
`Terrain` (world/types.ts): `heightAt`, `normalAt`, `surfaceAt`, `canopyAt`, `segmentHit`,
`raycast`, `lineOfSight(a, b, includeTrees)`, `roads`, `targetAreas`, `airbase`, `start`, `data`.
**One height function**: collision, ranging, line of sight, vehicle placement and the renderer
all read `heightAt`; the renderer never adds displacement the simulation does not know about.
`TerrainData` must be enough for a Web Worker to rebuild the same `Terrain` (the terrain view
builds tiles in a worker).

### Flight — `core/flight`

`createAircraftState(terrain, start)` · `stepFlightControls` · `stepFlight` · `stepWarnings` ·
`updateMassProperties(sim)` (call after fuel, ammunition or stores change).
Reads `sim.input`, `sim.avionics.gun` (PAC), `sim.stores` (mass, drag, asymmetry),
`sim.gun.rounds` (mass), `windAt`. Writes `sim.aircraft`. **External forces:** other systems add
body-frame force/moment to `aircraft.externalForceBody/externalMomentBody`; `stepFlight` applies
them once and clears them. **Sub-step interpolation:** `prevPosition/prevVelocity/
prevOrientation` hold the state at the start of the last flight step.
**Setters** (the only way other modules change flight state): `setFlapHandle(sim, 0|1|2)`,
`setGear(sim, down)`, `autopilotCommand(sim, 'toggle'|'disengage'|'mode')`,
`setAltitudeAlert(sim, metresAgl)`; also `engageAutopilot`, `disengageAutopilot`,
`trimAircraft`, `levelFlightThrottle`, `predictRecoveryClearance`. Testbed (tests and the flight
sandbox, import directly): `core/flight/testbed.ts`.
Derived fields others read: `wind` (mean + gust at the aircraft), `dynamicPressure`, `gLoad`,
`lateralG`, `axialG`, `stallAlpha`, `buffet` (0..1), `gLimitPositive/Negative`, `gearPosition`
(0..1), `groundCollision {clearance, timeToImpact}` (HUD break-X), `pac {aimPoint, aimValid,
errorAz, errorEl, …}`, `minG`/`maxG`. Fired rounds keep their spent cases on board (0.15 kg
each), so a round fired lowers the aircraft's mass by ≈0.54 kg (API), not 0.69 kg. Ground
contact tests the hull points measured on the model (`A10_GEOMETRY.hull`; with the gear down,
`gearContacts`).

### Weapons — `core/weapons`

`createGunState` · `roundTypeAt(load, n)` · `createRoundPool` · `createProjectileState` ·
`createStoresState(loadoutId, custom?)` · `LOADOUTS` · `stepGun` · `stepStores` ·
`stepProjectiles` · **ballistics** (`roundMass`, `dragFactor`, `integrateRound`,
`predictRoundImpact`) · **penetration** (`penetrationMm(type, speed)`).
The fire-control computer predicts with `predictRoundImpact`/`integrateRound` — the very same
functions that move live rounds (PLAN §6.1 rule 2).
Gun fires when `input.trigger === 2` (or 1 when the realism flag `twoStageTrigger` is off and
the trigger is pressed), `avionics.masterArm === 'ARM'`, `avionics.gunPac !== 'SAFE'`, rounds
remain (or unlimited). Any master mode.
What audio and the views rely on: `gun.rate` is the instantaneous rate (rounds/s) during spin-up
and spin-down; `gun.firing` is true while rounds leave; `gunStart`/`gunStop` carry exact times
(§3); `roundImpact` is emitted for every round that hits something, HEI included (audio and
effects draw HEI bursts from `roundImpact` and ignore `detonation` kind `'hei'`, so an HEI round
must not produce two bangs); `RoundPool.id` is unique per round (slots are reused, ids are not).
`StoresState` also always fills `rollInertia` (Σ m·x², kg·m²) and `dragMoment` (Σ CdA·x, m³,
yaw from asymmetric store drag).
Also exported: `muzzleState(ac, type, pos, vel)` (the undispersed start of a round fired now;
fire control uses it), `muzzleVelocity(type)`, `dragCoefficient(type, mach)`,
`flyRoundToRange`, `gunLineBody`, `RECOIL_IMPULSE`, `DISPERSION_SIGMA`, `fitApiPenetration`
(recomputes the §5 fit from the model), the pool helpers (`allocRound`, `freeRound`,
`clearRoundPool`), the loadout rules for the loadout screen (`stationAccepts(station, type)`,
`stationIssue`, `loadoutIssues(stations)`, `isRackType`, `STATION_COUNT`), `rearm(sim)` (ends any
open burst, refills the drum, restores the flight's loadout) and `jettisonStores(sim, stations |
'all')` (returns the number of stations cleared; racks drop with their stores, pods and the
AIM-9 rails stay; emits `storeReleased` with `bodyId: 0` until store bodies exist in wave 2).
Kinematic test bed: `core/weapons/testbed.ts`. `StoreType 'LAU-114'` is the dual-rail AIM-9
adapter. `gun.rate` = 65 × spin at all times, spin-down included; `gun.firing` = rounds are
leaving. A round that hits a scoring panel, or an outer layer with no armour behind it
(`passedThrough`), flies on through it; a ricochet flies on with the velocity
`resolveRoundHit` returns. An HEI `detonation` has the same `t` and position as its
`roundImpact`.

### Avionics — `core/avionics`

`createAvionicsState` · `applyCommands(sim)` · `stepFireControl(sim, dt)`.
Writes `avionics.gun: GunSolution` (pipper az/el from the eye, impact point, slant range, time
of flight, min/max range flags) and `avionics.release: ReleaseSolution`. Commands that belong
to another module's state (flaps, speed brake, autopilot, altitude alert → flight; jettison,
rearm → weapons; TGP/MAV slew and track → sensors) are applied by `applyCommands` through that
module's exported setter functions, never by writing the other module's private fields.
`applyCommands` handles **every** `Command` with the values listed in §3, calls the flight
setters (`setFlapHandle`, `setGear`, `autopilotCommand`, `setAltitudeAlert`) instead of writing
`sim.aircraft` fields, and emits `switch {name, value}` for each armament-panel switch, master
mode, profile, SOI, altitude-source and display change (audio clicks on them; nothing else emits
them). Switch-event names: `masterArm`, `gunPac`, `laserArm`, `tgpPower`, `altSource`,
`masterMode`, `profile`, `soi`, `leftMfd`, `rightMfd`, `osb`, `steerpoint`, `spi`, `slave`,
`gunSight`, `flaps`, `gear`, `autopilot`, `altitudeAlert`, `jettison`.
`createSim` calls `initAvionics(sim)` (steerpoints from the target areas and the airbase, the
SPI at the active steerpoint, one default weapon profile per store type from
`data/avionics.ts` `PROFILE_DEFAULTS`); a set-up that wants its own steerpoints or profiles
replaces the lists after `createSim`. State a HUD or display reads: `sight` (`'NONE' | 'GUN' |
'CCIP' | 'CCRP'`: which weapon sight to draw; the gun reticle also in CCIP when the gun is the
CCIP weapon), `ccipInvalid`, `gunSight`, `spi`, `steerpoints`/`activeSteerpoint`, `mfd`, `soi`,
`selectedProfile`/`profiles`, `buildDsmsView(sim, out)` for the stores page. `GunSolution` also
carries `minRange`/`maxRange` (2,000 / 12,000 ft, `FIRE_CONTROL` in `data/avionics.ts`),
`gunLineAz/El` (the gun cross), `groundSource`/`groundPlane`/`groundValid` (altitude source),
`roundType`, `impactSpeed`. For the sensors module: `sensorRequests` (HOTAS actions of this
step: avionics clears the list at the start of `applyCommands`, `stepSensors` reads it in the
same step) and `slaveRequest` (`{ sensors: 'ALL' | 'TGP', time }`, China hat forward/aft long).
Store fire control: `registerStoreBallistics(store, model)` (the weapons module registers each
store's ballistic model: the same integrator that moves the live store bodies) and
`predictStoreImpact`; the release solution stays invalid for a store without a model. An explicit
master mode that is not available is refused with a `message`. Also exported: `rearm`,
`jettison`, `previousMasterMode`/`nextMasterMode`/`modeAvailable`, `cycleProfile`,
`cycleSteerpoint`, `spiToSteerpoint`, `computeGunSolution`, `predictImpact`, `eyeWorld`,
`hudAnglesOfPoint`, the OSB and HOTAS tables.

### Targets — `core/targets`

`createTargetsState` · `createVehicle(sim, kind, x, z, heading, groupId)` ·
`populateScenario(sim)` · `stepTargets` · `segmentHitVehicle(sim, p0, p1, out: VehicleHit)` ·
`resolveRoundHit(sim, hit, roundType, velocity, out: RoundHitResult, sourceId?)` ·
`applyBlast(sim, position, chargeKg, fragmentKg?, weapon?, sourceId?)` · `VEHICLE_SHAPES`
(data/vehicles.ts). `sourceId` (a round id or a store body id) goes to the hit log; `weapon`
names the hit and kill records (`'HEI'` for 30 mm bursts; for bombs, rockets and missiles the
store name, e.g. `'MK-82'`, with the body id). The blast table is calibrated for a TNT-equivalent
charge plus the fragmenting case mass. For an HEI impact on a vehicle, call `resolveRoundHit`
BEFORE `applyBlast` at the same point in the same step (`applyBlast` then skips that vehicle,
so the burst counts once). `'passedThrough'` = a scoring panel, or a spaced layer (rear drums,
track run, gun barrel) with no armour behind it. Also exported: `VEHICLE_MODELS` (plates, parts,
components), `segmentHitVehicleAll`, `spawnGroup(sim, 'column'|'open'|'treeline'|'dugIn',
where, template)`, `digIn`, `findVehicle`, `isAlive`, `markTargetsMoved`, and the blast and
fragment helpers. `vehicle.heat` is a thermal model (engine deck, exhaust, running gear, fires;
cools over minutes) and `vehicle.fire` the larger of the inside and outside fires; a dug-in
vehicle's `position.y` is the floor of its pit, with the hull top 0.25 m above the ground.
`Vehicle.internal` is the targets module's own: other modules must not read or serialise it.
The targets module emits `vehicleDamaged` / `vehicleDestroyed` and appends `debrief.hits` and
`debrief.kills`. The weapons module emits `roundImpact` (with the outcome it got back).
Cook-offs and ammunition explosions emit `detonation` kind `'secondary'` with the `vehicleId`
(audio then skips the `vehicleDestroyed` boom of that vehicle in the same frame, so the blast is
heard once). `vehicleDestroyed` may arrive twice for one vehicle: destroyed (burning), then
`catastrophic: true` after a cook-off, with its `'secondary'` detonation in the same step; the
kill counts once (listeners such as kill messages must de-duplicate by `vehicleId`).
`vehicleDamaged` is sent for every hit that hurts a component. Ammunition trucks also emit
small `'secondary'` detonations for a while after exploding.

### Sensors — `core/sensors` (wave 2) · Debrief — `core/debrief` (wave 2)

State constructors and step functions as in their `index.ts`.

## 5. Data and numbers

- Every real-world constant lives in `src/a10/data/*.ts` as a plain `as const` object plus a
  `*_NOTES` record giving its `source` (an id in `data/sources.ts`) and `confidence`
  (`confirmed` · `approximate` · `estimate`). `docs/a10/REFERENCE_DATA.md` explains them.
- Ownership: `aircraft.ts` flight · `geometry.ts` aircraft/assets · `gun.ts`, `munitions.ts`
  weapons · `vehicles.ts` targets · `avionics.ts` avionics (fire control, weapon-profile
  defaults) · `sources.ts` foundation (ask to add a source).
- Tests check behaviour against these numbers (PLAN §16), never against magic numbers copied
  into the test.

### Decisions that cross modules (fixed here)

- **Penetration fit (PLAN §6.3).** API penetration is a function of impact speed,
  `P(v) = P_REF · (v / V_REF)^n`. The published "≈69 mm at 500 m, ≈38 mm at 1,000 m" are read
  as rounds fired **from an aircraft at 300 kn, 1,000 m above sea level, ISA, along the line of
  fire**. The weapons module computes `V_REF` (impact speed at 500 m) and `n` from its own
  ballistic model so that both points hold, and a unit test recomputes them. This keeps the
  plan's table (§6.3) and tests (§16) true for normal attacks, while a faster attack penetrates
  more, as it physically should.
- **Obliquity.** Effective thickness = plate thickness / cos(θ), θ = angle between the round's
  path and the plate normal. Ricochet when θ > 70°. Ground skip below ~8° impact angle on hard
  ground (weapons module decides the exact rule).
- **Dispersion.** 80 % of rounds inside a 5 mrad DIAMETER circle ⇒ circular normal with
  σ = 2.5 mrad / √(2 ln 5) ≈ 1.393 mrad per axis, drawn per round from `rng.gun`.
- **Gun geometry.** Muzzle position and gun-line depression come from `data/geometry.ts` and
  `data/gun.ts`. The pipper is drawn from the pilot's eye (collimated: direction only).
- **Rounds leave at exact times.** Emission time within a step = from the gun's rate
  integral; each round starts at the interpolated muzzle position/velocity at that instant and
  is integrated for the rest of the step.

## 6. The view

### Canvas and render pipeline

`App.tsx` creates one `<Canvas>` with `gl={{ antialias: true, stencil: true }}`, camera fov 50 (the default `settings.fov`; at 50° the HUD fills about a third of the screen height),
near 1, far 90 000. R3F sets sRGB output and ACES Filmic tone mapping on the renderer.

`RenderPipeline` (useFrame priority **1**) owns drawing: R3F's automatic render is therefore off
and **every pixel is drawn by a registered pass** (`view/pipeline.ts`):

| Order | Pass | Owner |
|---|---|---|
| 0–99 | offscreen sensor pictures (TGP, Maverick) into render targets | sensors (wave 2) |
| 100 | `world`: clear, draw R3F's default scene with the world camera | foundation |
| 200 | `cockpit`: clear depth, draw the cockpit scene (body frame) with the cockpit camera | cockpit |
| 300 | `hud`: stencil the combiner glass from the eye, draw collimated symbology | hud |
| 400–499 | overlays (e.g. weapon-camera picture-in-picture) | owners as needed |
| 900 | post-processing (optional, `prepareTarget` asks earlier passes to draw offscreen) | environment |

Rules:

- Only RenderPipeline has a useFrame priority > 0. Everything else uses the priorities in
  `view/frame.ts`: `sim` −100, `systems` −50, `camera` −20, visuals 0.
- **Tone mapping / colour.** Drawing to the screen (target null), three.js tone-maps (ACES) and
  sRGB-encodes in each material. Drawing into a render target it does NEITHER (linear HDR):
  a pass that shows a render target (sensor display, post) must tone-map and encode itself.
  Custom `ShaderMaterial`s end with `#include <tonemapping_fragment>` and
  `#include <colorspace_fragment>`.
- **Fog/haze.** Anything that fades with distance fades to the environment's horizon colour.
  The environment module owns `scene.fog` and exposes the current haze colour and density.
- **Terrain hooks (environment + terrain view).** `view/terrain/terrainMaterial.ts`
  `terrainUniforms.uThermal` (0 visible · 1 white-hot · 2 black-hot; terrain and trees share it;
  the sensors module sets it around its own render and restores it) and `uThermalParams.z`
  (picture gain; x and y are written every frame from the time of day). Vehicles have their own
  thermal hook (`view/vehicles`: `thermalUniforms`, `setThermalMode`). Live numbers:
  `view/terrain/terrainStats.ts` `terrainStreaming` (pending, tiles, drawCalls,
  drawnTriangles…). Terrain picking is the core's `Terrain.raycast`. The scene buffer of the
  post pass has a stencil buffer; bloom starts at luminance 1.7, so the HUD (≈0.9) does not
  glow.
- **Render order:** sky dome −1000 (no depth), clouds −10 (no depth write), opaque world 0,
  transparent effects ≥ 0.
- **Scenes:** the world scene is R3F's default scene. The cockpit module owns a separate
  `THREE.Scene` in BODY coordinates (cockpit, plus the aircraft's own nose/wings/engines as
  seen from inside, using the aircraft module's model) and renders it in its pass with a camera
  at the eye (near 0.03 m, far 40 m). The HUD module owns its own scene(s).
- **Cockpit camera and scene** (`view/cockpit/cockpitCamera.ts`, interface fixed, values owned
  by the cockpit module): `cockpitScene` and `cockpitCamera` (body coordinates: position = head,
  quaternion = head orientation relative to the body), `cockpitViewState.active`. The world
  camera in the cockpit view = aircraft pose ∘ cockpit camera pose. The HUD reads the cockpit
  camera so the symbology and the glass mask come from the same eye.
- **Exterior model:** in outside views `AircraftView` draws the aircraft in the world scene; in
  the cockpit view it hides itself and the cockpit pass draws the body-frame instance.
- **Cockpit display surfaces** (`view/cockpit/displays.ts`, cockpit module):
  `getDisplaySurfaces()` / `onDisplaySurfaces(fn)` give wave 2's MFDs two screens in the cockpit
  scene: `right` = the A-10A TV monitor's screen, `left` = its mirror image left of the ADI
  (hidden until `show(true)`: it covers the A-10A AoA gauge, clock and standby ADI). Each has a
  512-px canvas + `CanvasTexture` slot (draw, then `texture.needsUpdate = true`) or
  `setPicture(texture)` for a render target; unlit, not tone-mapped; `corners`, `normal`,
  `width`, `height` in the body frame. The cockpit passes are `cockpit` (200) and `vision` (450,
  grey-out / red-out overlay, cockpit view only). The rig's handle `cameraRigHandle.current`
  (`setLook`, `fovOverride`) and `useCameraRig(source)` / `useCockpit(source)` let sandboxes
  drive them with their own simulation.

### Cameras (cockpit module)

- `store.view`: `cockpit` (default) · `chase` · `flyby` · `orbit` · `weapon` · `target`.
- The camera rig (useFrame −20) places R3F's default camera (the world camera) for every view
  and, in the cockpit view, the cockpit camera at the head pose in body coordinates (head look,
  zoom, look-at-SPI, small g-induced head movement). It reads `viewInput` (`input/viewInput.ts`).
- The world camera's near plane is 1 m in the cockpit view (the aircraft itself is in the
  cockpit pass) and 0.5 m in outside views.

### Quality

`view/quality.ts`: `A10_QUALITY[level]` — terrain detail, trees, particles, shadows, sensor
resolution/rate, post-processing, clouds, model detail. Read with `getA10Quality()` per frame or
`useA10Quality()`. Adaptive downgrade (one step when < 45 fps for 3 s) is the environment
module's job, reusing the carrier's monitor through `src/engine`.

### Listener pose (`view/listener.ts`)

`listenerPose` (position, quaternion, velocity, inCockpit) is the world camera's pose, copied by
RenderPipeline every frame after the camera rig ran. Code outside the Canvas (audio) reads it.
`velocity` is a real-time finite difference of the camera position (it jumps when the view
changes); the audio module measures its own listener velocity over sim time for Doppler.

### Frame hooks (`view/frame.ts`)

`onBeforeSimSteps(fn(sim, realDt))` — input sampling. `onSimFrame(fn(events, sim, info))` —
effects, audio, UI, debrief displays. `frameInfo` — steps, alpha, realDt, simDt of this frame.

### Sharing the carrier's sky

The environment module makes the carrier's sky dome, sun/moon, haze, clouds, post-processing
chain and adaptive-quality monitor usable from `src/engine` by moving each component's body into
a prop-driven, carrier-free component and keeping the carrier file as a zero-prop wrapper
(behaviour identical; all carrier tests and a before/after screenshot of the carrier menu must
match). Facts from the analysis: bloom threshold is luminance ≈ 1.7; the effect order is heat →
bloom → vignette → ACES; the carrier persists settings under `fac-settings-v1` — the A-10 uses
`a10-settings-v1` and must never import the carrier store.

## 8. Input (input module)

Writes `sim.input` and queues `sim.commands` in an `onBeforeSimSteps` listener; writes
`viewInput` (look, zoom, cursor, clicks) for the camera and cockpit; handles view changes and
pause through the store. Owns bindings (persisted under `a10-bindings-v1`), devices (keyboard,
mouse, gamepad, any HID stick/throttle via the Gamepad API), dead zones, curves, the two-stage
trigger, short/long presses. Calls `applyTestInputOverride(sim.input)` last so tests can hold
controls. Default bindings: PLAN §12.

- **Gating.** *Live* = flight screen, not paused, settings closed, no binding capture (flight
  controls and commands). *App* = flight screen, no dialog or capture (views, pause). When not
  live, axes, the trigger and held buttons read 0, presses never fire (not even on release) and
  the throttle levers freeze where they are.
- **`viewInput`** (written by input, read by the camera rig and the cockpit): `lookX/lookY`
  look rates −1..1 (+right, +up); `lookDeltaX/Y` mouse pixels accumulated until `consumeLook()`;
  `zoomSteps` ±1 per wheel notch until `consumeZoom()`; `zoomHeld`, `lookAtSpi` held each
  frame; `cursorFree` toggled by Left Alt; `pointerX/Y` the pointer in NDC while the cursor is
  free; `click {x, y, button}` set on a canvas press only while `cursorFree` — the cockpit sets
  it to `null` when it handled the click; `centerView` is true for exactly one frame per press.
- **Escape.** The input layer never calls `preventDefault` on Escape and toggles pause after
  dispatch, only for an Escape nobody prevented. UI components prevent the Escapes they use
  (closing a dialog). Gamepad Start toggles pause directly.
- **APIs:** `useBindings`/`getBindingsConfig()`/`subscribeBindings()` (`bindingsStore.ts`),
  `isInputCaptureActive()`, `getControlsReference()`, `useControlsReference()` (re-renders on
  rebinding), `controlKeys(controlId, 'keyboard'|'gamepad')`.

## 9. Assets

- **Models** (`public/a10/models/`, produced by `scripts/a10/convert-ac3d.mjs` from
  `third_party/flightgear-a10/`): GLB files in OUR frames and metres. Exterior and cockpit in
  the body frame (origin = reference CG); stores in their own frame (origin at the suspension
  lugs, −Z forward). Node names keep the AC3D object names. Animated parts are wrapped in pivot
  nodes placed on their hinge, so rotating the pivot moves the part correctly. The converter
  writes to a staging folder and copies only changed files into `public/a10`, so it can run
  while dev servers serve it.
- **Sidecar** `public/a10/models/a10-meta.json`: source commit, CG, eye point, HUD combiner glass
  corners, muzzle, station positions, and every animation (pivot, axis, node list, input,
  range), the measured `hull` (ground-contact points with the gear up) and each store's
  hidden-by-default parts (`stores.<id>.toggles`, e.g. the Mk 82 AIR ballute, which a
  high-drag release shows on its copy). `data/geometry.ts` holds the values the simulation
  needs, copied from it and checked against it by `tests/unit/a10/assets.node.test.ts`.
- **Runtime instance** (`src/a10/assets`): `updateAircraftInstance(inst, sim, daylight)` poses
  surfaces, gear (from `aircraft.gearPosition`), fans and lights every frame, in every view
  (the cockpit pass updates its body-frame instance the same way);
  `updateAircraftDetail(inst, cameraPosition, fovDeg, viewportHeight)` hides the pilot, seat and
  cockpit tub (`inst.interior`) when the canopy is under about 9 px per metre (outside views).
- **Sounds** (`public/a10/sounds/`): WAV, mono, converted by a script from the FlightGear files
  (and later public recordings), budget < 3 MB.
- **URLs**: `a10Asset('models/x.glb')` (`src/a10/assets/urls.ts`, foundation) resolves against
  the one literal anchor `new URL('/a10/assets.json', import.meta.url)`, which Vite rewrites
  correctly in dev and in the build at any deploy path. Never build asset URLs from
  `import.meta.env.BASE_URL` or from a template literal inside `new URL(...)`: both break
  silently. Loaders live in `src/a10/assets/` (aircraft module).
- **Page URL**: always `/a10/` with the slash (a dev/preview plugin redirects `/a10`).
- **Credits**: every file under `public/a10/` has an entry in `CREDITS.md`; a unit test checks it.
  CREDITS.md's model/texture table is generated by `scripts/a10/convert-ac3d.mjs` and its sound
  table by `node scripts/a10/convert-credits.mjs` (from `scripts/a10/sounds-credits.json`); run
  the latter after `scripts/a10/sounds.mjs`. `tests/unit/a10/assets.node.test.ts` checks every
  file under `public/a10/{models,textures,sounds}` and the SHA-256 of the FlightGear sound
  originals.

## 10. Development

- **Sandboxes:** `/a10/?sandbox=<name>` (dev server) renders `src/a10/dev/sandboxes/<name>.tsx`,
  e.g. `?sandbox=terrain&preset=3000|1000|300&airbase=<agl>&time=&vis=&thermal=1|2`,
  `?sandbox=world&seed=N`. Effects (dev server): `window.__A10_FX__ = { warm(s), play(events, s),
  stats() }` replays events at exact times without stepping the sim.
- **URL flags** (`state/debugFlags.ts`): `?screen=flight`, `?scenario=`, `?quality=`,
  `?realism=`, `?seed=`, `?time=`, `?view=`, `?start=x,z,aglM,headingDeg,speedKias[,pathDeg]`
  (path angle + climb / − dive), `?arm=1`,
  `?paused=1`, `?mute=1`, `?ui=0`, `?fps=1`, `?sandbox=`. Audio (read by the audio module only):
  `?audiodebug=1` installs `window.__A10_AUDIO__` in a production build (always in dev:
  `state()`, `levels()` per bus in dBFS, `voices()`, `nodeCount()`, `trims()`,
  `setTrim(bus, v)`); `?audiomix=gun:1,engines:0.7` trims buses for the visit.
- **Test hook:** `window.__A10__ = { store, getSim, getTerrain, command(c), setInput(patch|null) }`.
- **Screenshots** (headless, software WebGL — slow; wait generously, force `?quality=low`):

```bash
VITE_CACHE_DIR=node_modules/.vite-<you> npx vite --port <port> --strictPort &
node scripts/shot.mjs --url "http://127.0.0.1:<port>/a10/?screen=flight&quality=low" --out .shots/<you>/x.png --wait 8000
```

  Always LOOK at your screenshots.

Tests that need Node APIs (`node:fs`, `node:path`) are named `*.node.test.ts`; they are
type-checked by `tsconfig.node.json` (Node types) instead of `tsconfig.app.json`. Other unit
tests read repository files with `import.meta.glob`.

### Checks before a module is done

```bash
npm run typecheck:app          # whole app; ignore errors in files you do not own
npx eslint <your files>
npx prettier --write <your files>
npx vitest run tests/unit/a10/<your tests>
```

### Working in parallel

Several agents edit this tree at once.

- Edit **only the files you own** (§11) and new files inside your own folders. Everything else
  is read-only; describe needed changes in your final report.
- Keep every export listed in §4 with its meaning; keep default exports of the view components
  mounted by `SceneRoot` / `App`.
- `tsc` may show errors in files others are editing: fix every error in yours, ignore the rest.
- No git commands that change state, no `npm install`, no formatters or `--fix` on files you do
  not own. Use your own dev-server port and `VITE_CACHE_DIR`; stop your server when done.
  Screenshots go in `.shots/<module>/` (git-ignored).
